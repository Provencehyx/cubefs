# DataNode 初学者指南

## 这是什么？

DataNode 是 CubeFS 的数据存储节点，负责存储实际的文件内容（不是元数据）。

```
用户写入文件 "hello.txt" 内容 "Hello World"
    │
    ├── MetaNode 存储：inode=123, name="hello.txt", extents=[{dp:1001, id:65}]
    │                  （文件叫什么、在哪里）
    │
    └── DataNode 存储：extent 文件内容 "Hello World"
                       （实际的字节数据）
```

## 为什么需要单独的 DataNode？

**问：为什么不把数据和元数据放在一起？**

| 维度 | 元数据 | 文件数据 |
|------|--------|----------|
| 数据量 | 小（KB级别/文件） | 大（可能 GB 级别） |
| 访问模式 | 高频、随机访问 | 流式读写 |
| 一致性要求 | 强一致（Raft） | 可以稍弱（链式复制） |
| 存储介质 | 可用内存/SSD | 必须用大容量 HDD |

分离后各自可以独立扩展和优化。

## 核心概念

### 1. DataPartition（数据分区）

一个 DataPartition ≈ 一个 120GB 的"数据桶"，存在一块磁盘上。

```
磁盘 /data/disk1/
├── datapartition_1001_3/    # 分区ID=1001, 副本数=3
│   ├── META                 # 分区元数据
│   ├── 1, 2, ... 64        # TinyExtent 文件
│   ├── 1024, 1025, ...     # NormalExtent 文件
│   └── wal_1001/           # Raft 日志
└── datapartition_1002_3/
```

**为什么是 120GB？**
- 太小：分区数量爆炸，管理开销大
- 太大：故障恢复时间长
- 120GB 是平衡点，坏一个分区几小时能修好

### 2. Extent（存储单元）

Extent 是 DataNode 的最小存储单位，分两种：

| 类型 | ID 范围 | 最大大小 | 用途 |
|------|---------|----------|------|
| TinyExtent | 1-64 | 无限追加 | 小文件（<1MB） |
| NormalExtent | ≥1024 | 128MB | 大文件 |

**为什么分两种？**
- **小文件问题**：每个文件一个 Extent → 海量小文件 → 海量磁盘文件 → 性能崩溃
- **解决方案**：多个小文件追加到同一个 TinyExtent

```
TinyExtent (ID=1)
┌────────────────────────────────────────┐
│ [file1: 512B] [file2: 1KB] [file3: 2KB] │ ← 多个小文件共享
└────────────────────────────────────────┘
删除 file2 → punch hole（不真的删除，留空洞）

NormalExtent (ID=1024)
┌────────────────────────────────────────┐
│ [大文件的一个 128MB 块]                  │ ← 独占
└────────────────────────────────────────┘
```

### 3. 副本复制（链式复制）

DataNode **不用 Raft 复制数据**，而是用链式复制：

```
Client 写入
    │
    ▼
Primary DataNode ──写入本地──┐
    │                       │
    │ 转发给 Follower1      │
    ▼                       │
Follower1 ──写入本地──┐      │
    │                │      │
    │ 转发给 Follower2│      │
    ▼                │      │
Follower2 ──写入本地 │      │
    │                │      │
    └────ACK─────────┼──────┘
                     │
              全部成功，返回Client
```

**为什么不用 Raft？**
- Raft 每次写要 2 次网络往返 (Leader→Follower, Follower→Leader)
- 链式复制只要 1 次往返（沿链传递，ACK 回传）
- 对于大数据量的流式写入，链式复制带宽利用率更高

### 4. Raft 在 DataNode 中的作用

Raft 只用于：
1. **成员变更**：增删副本节点
2. **随机写**：需要严格顺序的覆盖写

```go
// partition_raftfsm.go:37
func (dp *DataPartition) Apply(command []byte, index uint64) {
    // Raft 只处理随机写和特殊操作
    resp, err = dp.ApplyRandomWrite(command, index)
}
```

**设计理念**：
- 顺序追加写 → 链式复制（高吞吐）
- 随机覆盖写 → Raft（强一致）

## 学习路径

建议按以下顺序学习：

| 层级 | 主题 | 核心问题 |
|------|------|----------|
| Layer 1 | 启动与配置 | DataNode 如何启动？和 Master 如何交互？ |
| Layer 2 | 磁盘与空间管理 | SpaceManager/Disk 如何管理存储资源？ |
| Layer 3 | DataPartition | 分区的生命周期？元数据如何持久化？ |
| Layer 4 | Extent 存储 | Tiny/Normal Extent 的实现差异？ |
| Layer 5 | 链式复制 | 写请求如何在副本间传递？ |
| Layer 6 | Raft 一致性 | 哪些操作需要 Raft？为什么？ |
| Layer 7 | 数据修复 | 副本不一致时如何修复？ |

## DataNode vs MetaNode 对比

| 维度 | MetaNode | DataNode |
|------|----------|----------|
| 存储内容 | inode/dentry | 文件字节数据 |
| 存储引擎 | RocksDB（现在）/ B-Tree（曾经） | Extent 文件 |
| 数据量 | 较小（元数据） | 很大（实际文件） |
| 一致性协议 | 纯 Raft | 链式复制 + Raft |
| 分区大小 | 较小 | 120GB |
| 扩展单位 | MetaPartition | DataPartition |
