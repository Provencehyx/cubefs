# Master 初学者指南

## 一句话理解 Master

**Master 是 CubeFS 的大脑**——它不存储用户数据，但知道数据在哪、该放哪、谁还活着。

---

## 快速理解：一个请求的旅程

假设用户要创建一个名为 "my-vol" 的存储卷：

```
1. 用户请求
   curl -X POST "http://master:17010/admin/createVol?name=my-vol&capacity=100"
        │
        ▼
2. Master 接收请求（如果是 Follower，转发给 Leader）
        │
        ▼
3. Leader 处理
   ├── 检查：卷名是否合法？配额是否足够？
   ├── 选择：在哪些节点创建初始分区？
   │         └── 根据拓扑（Zone/NodeSet）选择节点
   │
   ├── 持久化：通过 Raft 写入集群元数据
   │         └── Leader → Follower 复制
   │         └── 多数节点确认后返回成功
   │
   └── 返回结果
        │
        ▼
4. 用户收到成功响应
   {
     "code": 0,
     "data": {"volumeName": "my-vol", ...}
   }
```

## 核心概念速览

### Master 管理什么？

| 资源 | 说明 | 存在哪 |
|------|------|--------|
| **Volume (卷)** | 用户的存储空间，类似一个大文件夹 | Master 内存 + RocksDB |
| **DataPartition** | 卷的数据分片，存实际文件内容 | DataNode 上 |
| **MetaPartition** | 卷的元数据分片，存文件名、目录结构 | MetaNode 上 |
| **DataNode** | 数据存储服务器 | 物理机器 |
| **MetaNode** | 元数据存储服务器 | 物理机器 |

### Master 不管什么？

- 用户的文件内容（那是 DataNode 的事）
- 文件的元数据（那是 MetaNode 的事）
- 客户端读写请求（客户端直接访问 DataNode/MetaNode）

## 三个关键设计

### 1. 为什么是 Raft + RocksDB？

**问题**：Master 挂了怎么办？

**方案**：
```
                    ┌─────────────────┐
写请求 ──────────▶  │  Master Leader  │
                    └────────┬────────┘
                             │ Raft 复制
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
        ┌──────────┐   ┌──────────┐   ┌──────────┐
        │Follower 1│   │Follower 2│   │  Leader  │
        │(备份)    │   │(备份)    │   │(主)      │
        └──────────┘   └──────────┘   └──────────┘
        
Leader 挂了？ → Follower 自动选举新 Leader → 服务继续
```

**核心思想**：通过 Raft 协议，3 个 Master 节点保持数据一致，1 个挂掉不影响服务。

### 2. 为什么需要 Zone 和 NodeSet？

**问题**：3 副本放在哪？

**错误做法**：随机选 3 个节点
```
3 副本都在同一机架 → 机架断电 → 数据丢失！
```

**正确做法**：按故障域分布
```
Zone1 (机房A): Replica1
Zone2 (机房B): Replica2
Zone3 (机房C): Replica3
→ 任意一个机房故障，数据依然可用
```

### 3. 后台任务为什么这么多？

**现实**：分布式系统时刻有节点挂、磁盘坏、网络抖。

**Master 的应对**：20+ 个后台任务持续监控和修复
```
checkHeartbeat   - 谁还活着？
checkPartitions  - 副本够不够？
recoverData      - 缺的副本补上
balanceLoad      - 太忙的节点减负
...
```

## 常见问题

### Q: Master 和 MetaNode 都存元数据，有什么区别？

| | Master | MetaNode |
|--|--------|----------|
| 存什么 | 集群元数据（卷列表、节点列表、分区分布） | 文件元数据（inode、目录树） |
| 数据量 | 较小（MB~GB 级） | 较大（可能 TB 级） |
| 一致性 | 强一致（单 Raft Group） | 强一致（每个 MP 一个 Raft Group） |

### Q: 为什么 Master 用单 Raft Group，MetaNode 用 Multi-Raft？

- **Master**：集群级元数据量小，单 Group 足够，简单可靠
- **MetaNode**：文件级元数据量大，必须分片（每个 MetaPartition 一个 Group）

### Q: Master 挂了会发生什么？

- **Leader 挂**：Follower 秒级选出新 Leader，写请求短暂不可用（1-3 秒）
- **Follower 挂**：无影响，Leader 继续服务
- **多数挂**：服务不可用（这是 Raft 的要求）
